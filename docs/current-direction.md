## Working assumption and owner decisions

The near-term emphasis is a working assumption: investigate a usable model-to-code
outcome while preserving the skill pack as the primary product. No actual consumer,
user, feature, implementation route or acceptance threshold has yet been selected
for this plan. If that emphasis is wrong, the owner should revise it before a
consumer implementation is chosen.

Before the first consumer milestone, answer these questions in the actual brief:

1. Who has the real job, what outcome do they need, and which existing repository
   and bounded feature will exercise it? Who accepts the model's meaning and result?
2. Which route fits: generated supported code, agent-written code from a reviewed
   model, or ordinary engineering? What remains outside the profile, including
   input validation, persistence, authentication, UI or concurrency?
3. What real successful and refused examples must hold, which policy choices are
   unresolved, and who will independently state/check the expected results?
4. What is the current effort and failure/review baseline? What observable benefit
   and maximum modeling/review overhead will the owner accept, over which changes?
5. Who can try the workflow without its author supplying missing steps, and what
   evidence will let the owner accept, revise or stop it?

Do not copy fictional decisions into these answers or manufacture baseline
numbers. A blocking policy question stays open. Tool passes do not resolve human
acceptance, real-use authorization or the example's Q_use.

## Milestones in dependency order

| Milestone | Acceptance evidence | Stop or re-scope when |
| --- | --- | --- |
| 1. Real consumer contract and fit | Named user/job, maintained target and decision owner; explicit route/profile fit and non-goals; independently frozen expected examples; observed baseline and owner-agreed benefit/overhead criteria. | No owner can judge success, a core need cannot be expressed without omission, or a blocking decision remains unanswered. Use ordinary engineering where appropriate; do not expand the language speculatively. |
| 2. Maintained feature and requirement change | One real consumer action reaches integrated behavior using the selected route; surrounding engineering is explicit; independent acceptance and existing regressions run. One meaningful requirement revision identifies stale evidence before reuse, then updates the maintained feature and rechecks it under renewed review. The owner assesses the result. | The result is still only a private fixture/report, integration changes the intended semantics, or model/code/expectation disagreements are hidden rather than investigated. |
| 3. Independent repeatability and value | A non-author operator completes a second agreed change from clean setup. Record actual effort, errors, review findings and support interventions against the baseline. Simplify or consolidate observed friction without weakening review or execution boundaries. | Overhead exceeds the agreed limit without the agreed benefit, author intervention remains necessary, or evidence cannot distinguish an improvement from one successful demonstration. Stop or change the approach instead of adding another wrapper. |

These gates do not promise a measured improvement or choose the missing criteria.
A green fictional replay is not milestone 1 or 2. A meaningful profile extension
needs a specific consumer requirement, separate scope and independent checks.

## Bounded supporting work after this plan merges

The primary product step remains the owner answering the consumer questions.
Two supporting outcomes can improve the current baseline without pretending to
satisfy those questions. These are dependencies and boundaries, not a second live
backlog; consult canonical task records for any later claim or result.

- **Current runtime status:** reconcile the implementation/status overlay and
  rollout account with actual source and CI. Preserve dated plans and evidence;
  distinguish implemented behavior, observed checks and actual activation. Do not
  activate dispatch, migrate claims, reopen held recovery work or expand runtime.
- **Cold operator observation:** an independent operator follows the current public
  modeling path from its declared setup, recording actual commands, missing steps,
  friction, unresolved choices and unavailable checks. Fix only observed guide or
  navigation defects under bounded review. Do not add a wrapper by default or
  relabel an expert-guided fictional replay as a real consumer or value result.

Recommend runtime maintenance only until a demonstrated consumer need establishes
a dependency: correctness/regression fixes and accurate operating
information remain useful. This prioritization changes no authority or rollout
policy. Keep runtime activation and any future integration separately reviewed.
Pause speculative CLI/report proliferation, language/standards expansion and
runtime features. Revisit those choices from consumer evidence, not accumulated
fixture passes. Review and merge each bounded change before assigning more work.
